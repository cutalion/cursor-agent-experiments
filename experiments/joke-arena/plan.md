# Joke Arena Rails Experiment Spec

## Goal
Build a complete Ruby on Rails web application where users compare jokes generated by two configured LLM models. A user enters a prompt, the server generates two jokes, the user votes on the result, and the application updates a leaderboard of model scores.

The implementation should be ready to run locally, documented, tested, and suitable for evaluating an agent's ability to build a small full-stack Rails product.

## Required Stack
Use these technologies:

- Ruby on Rails.
- SQLite for development and test.
- Hotwire and Turbo for dynamic page updates.
- ERB views.
- Some JavaScript where useful, preferably through Stimulus.
- CSS for a responsive and usable interface.
- RubyLLM through the `ruby_llm` gem for model calls.
- Automated tests.

Do not replace the required stack with a single-page frontend framework, a different database, or a different LLM client.

## Product Behavior
The app is a "joke arena" for comparing LLM-generated jokes.

### Main Page
The main page must let a user enter a prompt for a joke.

It should include:

- A clear title and short explanation.
- A prompt input.
- A submit action that starts generation.
- Validation feedback for invalid prompts.
- A link to the leaderboard.
- A useful empty or disabled state if the app cannot generate a comparison because fewer than two models are available.

Example user prompt:

```text
Tell me a joke about databases.
```

### Joke Generation
When the user submits a valid prompt:

1. The server chooses two available configured models.
2. The server asks each model to generate one joke for the prompt.
3. The generated jokes are stored so the comparison can be shown and voted on.
4. The user sees both jokes in a comparison view.

The app should ask for exactly one concise joke per model. It should handle provider failures gracefully and show a friendly error instead of crashing.

### Comparison Page
The comparison view must show:

- The original prompt.
- Two generated jokes.
- Four voting choices:
  - First joke is better.
  - Second joke is better.
  - Both are good.
  - Both are bad.

The two model identities should be hidden before the user votes, so the user judges the jokes rather than the model names.

After the user votes:

- The vote is recorded.
- Scores are updated.
- The result is shown.
- The model names are revealed.
- The user can start another comparison or visit the leaderboard.

The app must prevent a duplicate vote from applying score changes more than once.

### Leaderboard Page
The leaderboard page must show all configured models with ranking and score information.

It should include enough information for a user to understand model performance, such as:

- Rank.
- Model display name.
- Provider or source.
- Score.
- Win/loss or vote statistics.
- Number of completed comparisons.

Models should be ordered by strongest performance first. If no models are configured or no comparisons have happened yet, show a clear empty state.

## Model Configuration
Models must be configurable without changing controller or view code.

The implementation may choose the exact config file shape and persistence strategy, but it must support:

- Adding a model through configuration.
- Disabling a model through configuration.
- Storing a display name.
- Storing the RubyLLM provider/source.
- Storing the provider-specific model identifier.
- Supporting custom or not-yet-known model identifiers when RubyLLM requires that.

Do not hardcode the two competing models in the request flow.

The README must explain how to add, disable, and use models.

## RubyLLM Requirements
Use RubyLLM for real generation outside tests.

The implementation must:

- Configure RubyLLM from environment variables or Rails credentials.
- Support common provider credentials such as OpenAI, Anthropic, Gemini, OpenRouter, and local or OpenAI-compatible endpoints where practical.
- Use RubyLLM's documented chat interface to call the selected model.
- Read generated text from the RubyLLM response.
- Keep provider credentials out of logs, rendered HTML, and committed files.
- Handle RubyLLM configuration errors, provider errors, timeouts, and blank responses.

The implementation may decide how to organize RubyLLM integration internally.

## Scoring Rules
Use a clear and deterministic scoring system.

The exact point values are up to the implementation, but they must satisfy:

- Choosing the first joke benefits the first model more than the second.
- Choosing the second joke benefits the second model more than the first.
- Choosing "both are good" benefits both models equally.
- Choosing "both are bad" penalizes or negatively records both models equally.
- Every completed vote updates both participating models' comparison counts exactly once.
- Score updates must be atomic and resistant to double submission.

The README or UI should make the scoring easy to understand.

## UI Requirements
The UI should be responsive and accessible.

Required qualities:

- Works on desktop and mobile.
- Uses semantic headings, labels, and buttons.
- Shows loading or pending states during generation and voting.
- Shows user-friendly errors.
- Escapes user input and generated text.
- Does not reveal model names before voting.
- Reveals model names after voting.
- Provides clear navigation between the main page and leaderboard.

Use Turbo for the central interaction flow where appropriate, such as replacing the prompt form with the comparison or replacing vote controls with the result. Keep normal HTML behavior working when practical.

## Testing Requirements
Write tests that cover the application behavior.

Tests should include:

- Prompt validation.
- Successful joke generation flow with two generated jokes.
- Friendly handling of generation failures.
- Voting for the first joke.
- Voting for the second joke.
- Voting "both are good".
- Voting "both are bad".
- Duplicate vote protection.
- Score and statistics updates.
- Leaderboard ordering and display.
- Model configuration loading or equivalent setup behavior.
- Main user flow through a browser/system test or equivalent high-level test.

The exact test organization is up to the implementation.

## Test Isolation From Real LLMs
Tests must not perform real LLM requests.

Required constraints:

- Stub or fake RubyLLM calls in tests.
- Ensure tests are deterministic.
- Prevent accidental external network calls in tests, using WebMock or an equivalent mechanism if needed.
- Do not require provider API keys to run the test suite.
- Do not use recorded real LLM responses that could leak provider data or make tests brittle.

Tests should still prove that the production code is wired to RubyLLM correctly enough that real calls can work when credentials and configured models are provided.

## Error Handling
Handle at least:

- Blank or invalid prompts.
- Fewer than two available models.
- RubyLLM configuration errors.
- Provider errors or timeouts.
- Blank model responses.
- Duplicate votes.
- Invalid vote choices.

Errors shown to users should be concise and safe. Logs may contain debugging context, but must not expose secrets.

## Documentation
The implementation must include setup and usage documentation.

Document:

- Required Ruby and Rails versions, or how to use the versions generated by the app.
- Dependency installation.
- Database setup.
- How to configure provider credentials.
- How to configure models.
- How to run the app locally.
- How to run the test suite.
- That tests use stubs/fakes and do not call real LLM providers.
- Any browser or driver requirements for system tests.

## Acceptance Criteria
The implementation is complete when:

- The Rails app boots locally.
- The main page accepts a joke prompt.
- Two jokes can be generated from two configured RubyLLM models outside tests.
- The comparison page hides model names before voting.
- The user can vote for either joke, both good, or both bad.
- Scores and leaderboard statistics update correctly.
- Duplicate votes cannot double-apply score changes.
- The leaderboard ranks configured models.
- Models can be added or disabled through configuration.
- Tests pass without real LLM API calls.
- Setup and run instructions are clear.
- The UI is usable, responsive, and accessible.

## Evaluation Criteria
Judge agent outputs on:

- Product completeness.
- Correct use of Rails, SQLite, Hotwire/Turbo, and RubyLLM.
- Quality of the model configuration approach.
- Correctness of voting, scoring, and duplicate vote handling.
- Reliability of error handling.
- Test coverage and test determinism.
- No real LLM requests during tests.
- Code organization and maintainability.
- Setup documentation quality.
- UI quality, especially relative to mockups if provided.
